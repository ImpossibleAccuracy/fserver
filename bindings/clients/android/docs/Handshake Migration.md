# Миграция рукопожатия

### Переход от текущего рукопожатия к двухуровневой схеме

> Рабочий документ. Версия 1 (черновик).
> Целевое устройство протокола описано в `../../../../docs/Connection Protocol.md` (далее по тексту —
> «протокол»); здесь — только разница и порядок работ. Направление перехода:
> **текущее состояние → целевое**.
>
> Область: модули `:net` и `:net:transport` клиента. Изменения в `:core` и `:app` перечислены
> списком в §5, но не планируются здесь.

---

## 1. Что есть сейчас

### 1.1. Два подтверждения, оба до аутентификации

| Где | Что | Файл |
|---|---|---|
| Транспортный уровень | Входящее соединение попадает в поток `incoming`; пользователь подтверждает **до** `InboundConnection.accept()` | `connection/ConnectionManagerImpl.kt:275` |
| Уровень рукопожатия | `PeerAuthenticator.verify` + согласование словаря, до отправки `HELLO_ACK` | `handshake/HandshakeNegotiator.kt:179` |

Первое означает, что ни один байт постороннего не доходит до разбора кадров, пока пользователь не
нажал кнопку. Это же означает, что любое соединение требует его участия.

### 1.2. Порядок обмена

```
инициатор                                        отвечающий
    │── HELLO ──────────────────────────────────────▶│
    │                                                │ проверка версии
    │                                                │ PeerAuthenticator.verify  ← подтверждение
    │                                                │ dictionary.negotiate
    │◀───────────────────────────────────── HELLO_ACK │
    │── DESCRIPTOR_REQUEST ─────────────────────────▶│
    │◀────────────────────────────── DESCRIPTOR_RESPONSE
    │── READY ──────────────────────────────────────▶│
    │                                                │
    └─ link(): SecureChannel создаётся здесь, в самом конце
```

Существенно: `SecureChannel` собирается в `link()` (`handshake/HandshakeNegotiator.kt:205`), то есть
**всё рукопожатие целиком идёт открытым текстом**. Плюс `PassthroughCryptoProvider`
(`security/Crypto.kt:48`) не шифрует и после.

### 1.3. Дублирование `HandshakeHello` и `PeerDescriptor`

| Поле | `HandshakeHello` | `PeerDescriptor` |
|---|:--:|:--:|
| `deviceId` | ✓ | ✓ |
| `displayName` | ✓ | ✓ |
| публичный ключ / отпечаток | `publicKey` | `advertised.fingerprint` (производная) |
| словарь сообщений | `dictionary` | `advertised.dictionaryId` + `dictionaryVersion` |
| диапазон версий | `minVersion`/`maxVersion` | `advertised.protocolVersions` |
| `keyExchangeKey`, `maxFrameSize`, `cipherSuite` | ✓ | — |
| `kind`, `accessMode` | — | ✓ |

`DESCRIPTOR_REQUEST`/`DESCRIPTOR_RESPONSE` — это, по сути, повторная отправка `HELLO` плюс `kind`.
Именно этот дубль устраняется в первую очередь.

### 1.4. Что объявляется наружу

`discovery/PeerDiscoveryImpl.kt:136` жёстко публикует: идентификатор устройства, имя, отпечаток,
диапазон версий, идентификатор и версию словаря. Состав захардкожен, настройкой не управляется.

Отдельно: самофильтрация найденных устройств сравнивает объявленный идентификатор со своим
(`discovery/PeerDiscoveryImpl.kt:66`) — то есть зависит от того, что идентификатор публикуется.

## 2. Разница потоков

| | Сейчас | Целевое |
|---|---|---|
| Кто подтверждает входящее | Пользователь, на каждое соединение, до разбора кадров | Никто на уровне приветствия; пользователь — только при переходе к аутентификации |
| Что видно без аутентификации | Идентификатор, имя, публичный ключ, словарь, версии | Диапазон версий и перечень методов |
| Когда создаётся защищённый канал | В конце рукопожатия | Сразу после аутентификации, до обмена дескрипторами |
| `probe` | Полное рукопожатие с подтверждением, затем разрыв | Публичное приветствие, без подтверждения |
| Число соединений на сопряжение | Одно | Два: приветствие и соединение (см. протокол §4.4) |
| Согласование размера кадра | В `HELLO`, до аутентификации | В дескрипторе; до запечатывания лимит локальный |
| Выбор способа доступа | `accessMode` — заглушка, ни на что не влияет | Идентификатор метода, определяющий паттерн и примитивы |

## 3. Судьба типов

| Тип | Файл | Что с ним |
|---|---|---|
| `HandshakeHello` | `handshake/HandshakeHello.kt` | Заменяется на `PublicHello` (4 поля). Приватные поля уходят в дескриптор, `keyExchangeKey` — внутрь метода аутентификации |
| `FrameKind` | `wire/FrameKind.kt` | `DESCRIPTOR_REQUEST`/`DESCRIPTOR_RESPONSE` → один `DESCRIPTOR`; добавляется `AUTH` |
| `PeerAuthenticator` | `security/PeerAuthenticator.kt` | Становится реализацией `AuthMethod` для сверки строки, а не универсальным подтверждением. Сигнатура `verify(candidate, confirmationCode)` переносится почти без изменений |
| `CryptoProvider` | `security/Crypto.kt` | Переформулируется: не «дай обмен ключами и шифрование», а «прогони паттерн рукопожатия» |
| `PeerIdentity` | `security/Identity.kt` | Теряет `displayName` — имя всегда данные дескриптора, никогда не идентичность. Остаётся `deviceId` + `publicKey` |
| `PeerDescriptor` | `peer/PeerDescriptor.kt` | Вложенный `Advertised` выделяется в отдельный тип `AdvertisedPeer` (данные обнаружения). `AccessMode` удаляется целиком |
| `NegotiatedParameters` | `security/NegotiatedParameters.kt` | Собирается в два шага: часть до запечатывания, часть после обмена дескрипторами |
| `SecureChannel` | `security/SecureChannel.kt` | Должен быть пригоден к использованию **внутри** рукопожатия, а не только после |
| `TransportCapabilities` | `spi/Transport.kt:62` | `isLinkEncrypted` + `requiresPeerConfirmation` схлопываются в `ChannelSecurity`; добавляется источник приветствия |
| `ConnectionManager.Profile` | `connection/ConnectionManager.kt:85` | Разделяется: `Greeting` (публичный, из приветствия) и `Profile` (после аутентификации) |
| `ConnectionManager.IncomingRequest` | `connection/ConnectionManager.kt:91` | Эмитится не при приёме сокета, а при переходе собеседника к аутентификации |
| `FramePump`, `Envelope`, `ByteReader`/`ByteWriter`, `PeerSession`, `ConnectionPolicy`, SPI обнаружения | | **Без изменений** |

## 4. Порядок работ

Каждый этап оставляет модуль собираемым и тесты зелёными. Э1–Э3 независимы между собой; Э4 —
единственный рискованный; Э5 и Э6 зависят от Э4 строго по порядку.

> **Состояние: Э1–Э8 выполнены.** `:net` — 76 тестов, `:net:transport:android` — 12, все зелёные;
> оба транспортных модуля собираются. Остаётся Э9 (настоящая крипта).
> `:core` и `:app` сознательно оставлены несобирающимися (см. §5).

### Э1. Разделить типы, почти не трогая провод

- `PeerIdentity` теряет `displayName`.
- `PeerDescriptor.Advertised` выделяется в `AdvertisedPeer`; обнаружение отдаёт его, рукопожатие —
  `PeerDescriptor`.
- `AccessMode` удаляется (`peer/PeerDescriptor.kt:20`) вместе с полем в `LocalIdentity` и
  `EphemeralIdentityStore`.

Готово, когда: `:net:test` зелёный, поведение снаружи не изменилось.

### Э2. Возможности транспорта

- В `spi/Transport.kt`: `ChannelSecurity` вместо пары булевых полей, плюс источник приветствия
  (`провод` / `транспорт` / `отсутствует`).
- `NearbyConnectionsTransport` объявляет `Sas` и источник `транспорт`;
  `MulticastDnsTransport` и прямой IP — `None` и источник `провод`.

Пока это читают только логи. Готово, когда: транспорты объявляют корректно, ничего не сломано.

### Э3. `AuthMethod` как SPI, с заглушкой

- `PeerAuthenticator` → `AuthMethod`; добавляется кадр `AUTH` с N раундами.
- `PassthroughAuthMethod` — держит место под PAKE ровно так же, как `PassthroughCryptoProvider`
  держит место под X25519. Позволяет отложить выбор PAKE (протокол §8.1), не
  блокируя прототип.
- `SasAuthMethod` — оборачивает существующую сверку `confirmationCode`, даёт рабочий сквозной путь
  для Nearby.
- Проверка из протокола §6.3, правило 1: транспортный метод принимается только если его объявил
  собственный транспорт этого соединения. **Реализуется здесь, не позже.**

Порядок рукопожатия пока прежний. Готово, когда: путь Nearby работает через `SasAuthMethod`,
`handshake/HandshakeNegotiatorTest` адаптирован.

### Э4. Инверсия порядка — ядро изменения

- `SecureChannel` учится работать в рукопожатии: `expect`/`write` идут поверх него, а не напрямую
  через `FramePump`.
- `link()` разъезжается: канал запечатывается сразу после `AUTH`, дескрипторы идут после.
- `dictionary.negotiate()` переезжает за запечатывание.
- `DESCRIPTOR_REQUEST`/`DESCRIPTOR_RESPONSE` → один `DESCRIPTOR`, отправляемый обеими сторонами
  независимо.
- Байты `HELLO`/`HELLO_ACK` подаются в `AuthMethod` как prologue.

Готово, когда: есть тест, что дескриптор **не появляется** в открытом виде ни в одном кадре.

### Э5. Минимальный `HELLO`

- `HandshakeHello` → `PublicHello`: диапазон версий, перечень методов, параметры метода.
- `maxFrameSize` и `cipherSuite` уезжают в дескриптор; до запечатывания каждая сторона применяет
  свой локальный лимит.

Готово, когда: есть тест, что `HELLO` не содержит идентификатора устройства и имени.

### Э6. Двухфазный `ConnectionManager`

- `probe()` возвращает `Greeting`, не пишет в реестр профилей.
- `connect(peer, credentials)`; **результат `probe` на вход не принимается** — приветствие звучит
  заново в соединении (протокол §4.3).
- `Profile` заполняется только после аутентификации.
- `IncomingRequest` эмитится при переходе собеседника к `AUTH`, а не при приёме сокета. Самая
  крупная перестройка в `connection/ConnectionManagerImpl.kt`.
- При источнике приветствия `транспорт` `probe` не открывает соединения — берёт данные из
  обнаружения.

Готово, когда: `connection/ConnectionManagerTest` покрывает оба источника приветствия и
расхождение метода между приветствием и соединением (протокол §4.5).

### Э7. Объявление по настройке

- Состав объявления (`discovery/PeerDiscoveryImpl.kt:136`) переезжает в конфигурацию.
- Добавляются описание устройства и перечень методов; убираются отпечаток, словарь и —
  в зависимости от решения по §8.2 ниже — идентификатор устройства.
- Самофильтрация найденных устройств (`discovery/PeerDiscoveryImpl.kt:66`) перестаёт зависеть от
  публикации идентификатора: вместо него случайное значение на запуск процесса, узнаваемое только
  самим устройством.
- Скрытый режим (ТЗ §3.2) не объявляется вовсе.

### Э8. Ограничение частоты

Обязательно, потому что Э6 снимает подтверждение пользователя, которое сейчас работает как
естественный ограничитель.

- Предел одновременных рукопожатий до аутентификации.
- Ограничение частоты по адресу источника.
- Счётчик неудачных попыток на принимающей стороне, стойкий между соединениями, с нарастающей
  задержкой — перечень методов в приветствии наводит на слабейшее устройство
  (протокол §7.7).
- Проверка длины кадра против локального лимита **до** выделения памяти: `ByteReader` читает
  префикс длины, и до Э6 он недостижим для постороннего, а после — достижим.

### Э9. Настоящая криптография

Вне этой миграции, но до любого выпуска: X25519 + ChaCha20-Poly1305 вместо
`PassthroughCryptoProvider`, реальный PAKE вместо `PassthroughAuthMethod`.

**До Э9 «за аутентификацией» — заявление, а не свойство.** Кадры идут открытым текстом
независимо от того, в каком порядке они отправлены. Интерфейс не должен обещать приватность
раньше этого этапа.

Nearby — единственный транспорт, где до Э9 защита не является ложной: канал шифрует сам транспорт,
а сверка цифр его аутентифицирует.

## 5. Что ломается за пределами `:net`

Не планируется здесь, перечислено для оценки объёма.

- `data/repository/DevicesRepositoryImpl.kt` — читает `profile.negotiated.peerDescriptor` для
  устройств без сессии (строки 66–81). После Э6 у приветствия дескриптора нет; список устройств
  начинает показывать объявленные, непроверенные данные.
- `domain/model/ForeignDevice.Handshake` — состав меняется вслед за `Profile`.
- `handshakeByDeviceId`, `handshake(host, port)`, `handshake(payload)` — сейчас все три вызывают
  `probe`, то есть полное рукопожатие. Становятся приветствием; соединение — отдельный вызов с
  учётными данными от пользователя.
- Поток `incoming` — момент появления запроса смещается, диалог подтверждения перестаёт быть
  «подтвердите соединение» и становится частью выбранного метода аутентификации.
- Интерфейс: форма ввода между приветствием и соединением — новый экран, которого сейчас нет.

## 6. Тесты

Существующие, которые придётся править: `handshake/HandshakeNegotiatorTest`,
`connection/ConnectionManagerTest`, `SessionTest`, вспомогательный `support/XorCrypto`.

Новые, которые стоит завести вместе с соответствующими этапами:

| Этап | Проверка |
|---|---|
| Э3 | Метод, объявленный только собеседником, но не собственным транспортом, отвергается |
| Э4 | Дескриптор не встречается ни в одном кадре открытым текстом |
| Э4 | Изменение байта в `HELLO` роняет аутентификацию (привязка транскрипта) |
| Э5 | `HELLO` не содержит идентификатора устройства, имени и публичного ключа |
| Э6 | Расхождение метода между приветствием и соединением прерывает попытку, а не продолжает по данным приветствия |
| Э6 | Приветствие при источнике `транспорт` не открывает соединения |
| Э8 | Отказ после N неудачных попыток; счётчик переживает разрыв соединения |
