# Шифрование хранилища

### Шифрование файлов на диске (at-rest), политика по хранилищам, расширяемые методы

> Рабочий документ. Версия 2 (черновик). Описывает целевое устройство независимо от текущей
> реализации.
>
> Опирается на ТЗ §3.4 (синхронизация, разгрузка), §3.6 (безопасность и шифрование), §3.9 (экспорт).

---

## 1. Задача

ТЗ §3.6: «файлы шифруются в хранилище (at-rest), транспорт шифруется всегда». Документ решает:

- где файл расшифровывается — при передаче или только при доступе;
- что делать с хранилищами, которые шифровать нельзя;
- как живут рядом зашифрованные и ещё не зашифрованные файлы;
- как приложение подключает собственный метод шифрования.

## 2. Модель угроз

### 2.1. От кого защищаемся

- **Кража или изъятие носителя** — диск, SD-карта, извлечённая копия данных приложения.

### 2.2. От кого не защищаемся, осознанно

- **Недоверенный сервер.** Ключи доступны серверу (ТЗ §3.6: ИИ расшифровывает файлы). Это нужно
  честно показывать в интерфейсе.
- **Скомпрометированное работающее устройство** (root, вредонос с доступом к процессу): ключ в
  памяти, файлы читаются так же, как их читает приложение.
- **Сквозное шифрование (E2E)**, при котором сервер не может прочитать файлы, — вне рамок
  документа и отложено на далёкое будущее. Схема ниже его не закрывает: E2E ляжет отдельным слоем
  поверх движка, со своим ключом пользователя.

## 3. Ключевое решение: шифрование локально для устройства

**Файл расшифровывается при чтении из хранилища. По сети передаётся открытый текст внутри
зашифрованного канала (Протокол соединения).** У каждого устройства свой ключ и, возможно, свой
метод; другие устройства о них не знают.

Почему не передавать шифротекст:

| Причина                  | Что сломалось бы                                                                                                                                                                                |
|--------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Хэш содержимого          | Векторы версий, «одинаковое содержимое — не конфликт», подтверждение `evict` по хэшу (ТЗ §3.4) сравнивают хэши. Со случайным nonce одно содержимое даёт разный шифротекст на каждом устройстве. |
| Разные ключи и методы    | Получателю пришлось бы знать ключ и метод отправителя. Кастомный метод одного приложения просочился бы в протокол, сторонние клиенты перестали бы понимать данные.                              |
| Хранилища без шифрования | Получатель, пишущий в общую медиатеку, всё равно расшифровывает.                                                                                                                                |
| ИИ на сервере            | Расшифровывает в любом случае.                                                                                                                                                                  |

Следствия:

- **Хэш содержимого всегда считается от открытого текста.** Индекс, протокол и движок видят только
  его.
- **Шифрование не меняет версию.** Перешифровка, смена метода, ротация ключа не трогают вектор
  версий: содержимое не изменилось (ТЗ §3.4: «новая версия — только при изменении содержимого»).
- **Экспорт (ТЗ §3.9) выгружает открытый текст.**

## 4. Место в архитектуре

Шифрование — декоратор над файловой системой: `EncryptedFileSystem(inner, policy, ciphers, keys)`.
Чтение отдаёт открытый текст, запись принимает открытый текст и пишет шифротекст. Движок
синхронизации о шифровании не знает.

Сведения о шифровании конкретного файла хранит индекс, а не движок (см. §6).

## 5. Политика по хранилищам

Не всякое хранилище можно шифровать: файлы в общих папках читают другие приложения. Каждый
источник объявляет, поддерживает ли он шифрование, а политика задаётся по папке.

| Источник                        | Шифрование                                              | Почему                                                                                                              |
|---------------------------------|---------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------|
| Внутреннее хранилище приложения | можно                                                   | Приватное. На Android его уже шифрует система (FBE), поэтому выигрыш — защита от root и извлечения резервной копии. |
| Каталог / дерево (SAF)          | только папка, выделенная под FServer (бэкап, разгрузка) | Шифротекст в пользовательской папке ломает все остальные приложения.                                                |
| Медиатека, Загрузки             | никогда                                                 | Галерея и файловые менеджеры должны видеть файлы.                                                                   |
| Общие файлы (share)             | невозможно                                              | Только чтение.                                                                                                      |

Политика папки: `Off` / `Required`. Интерфейс показывает статус каждой папки: «зашифровано»,
«не шифруется: системное хранилище», «шифруется: N в очереди».

## 6. Смешанное состояние

В одной папке одновременно бывают зашифрованные и открытые файлы: пользователь положил файл сам,
политику только что включили, метод сменили.

### 6.1. Источник истины

- **Индекс** хранит состояние файла: `none` / `pending` / `<id метода>, <id ключа>`.
- **Заголовок файла** описывает его самостоятельно (§7.1) и служит перепроверкой.

Доверять одному заголовку нельзя:

- открытый файл, случайно начинающийся с сигнатуры, был бы принят за шифрованный;
- **подмена на открытый текст (downgrade):** злоумышленник кладёт открытый файл на место
  шифрованного. Если политика папки `Required`, а индекс не говорит `pending`, открытый текст
  отвергается.

### 6.2. Фоновая миграция

Одна процедура для `pending → зашифрован`, смены метода и ротации ключа:

1. записать результат во временный файл рядом;
2. fsync;
3. атомарно переименовать поверх исходного;
4. обновить индекс.

Падение на любом шаге оставляет либо старый, либо новый файл целым. Вектор версий не меняется (§3).

### 6.3. Новые файлы

- Пришедшие по сети и созданные через ядро пишутся через декоратор и шифруются сразу.
- Появившиеся в папке в обход ядра остаются открытыми, пока их не заберёт миграция.

### 6.4. Открытые хвосты

Шифрование хранилища бессмысленно, если открытая копия лежит рядом. Под ту же политику попадают
превью, кэши и временные копии — в том числе копии файлов, полученных через «Поделиться».

## 7. Формат файла

### 7.1. Заголовок

```
magic | версия формата | размер сегмента | размер nonce | размер тега | id метода | id ключа | соль
```

Соль — случайные 16 байт на файл. Заголовок целиком входит в AAD каждого сегмента: изменённый
заголовок не откроется, а сегмент не переносится из одного файла в другой.

### 7.2. Сегменты

Файл режется на сегменты (порядка 64 КиБ), каждый запечатывается AEAD отдельно:

- сегмент на диске — `nonce | шифротекст`; nonce **случайный при каждом запечатывании** и
  хранится рядом. Выводить его из номера сегмента нельзя: запись по смещению перезапечатывает
  сегмент тем же ключом, и повтор nonce в GCM раскрывает открытый текст и позволяет подделку;
- AAD сегмента = заголовок + номер сегмента + флаг «последний»: перестановка сегментов и
  обрезка файла по границе сегмента ломают проверку;
- пустой файл — один пустой последний сегмент;
- запись по смещению перезапечатывает затронутые сегменты (и прежний последний — при росте
  файла), `truncate` перезапечатывает новый последний.

Подмена сегмента его же старой версией (откат) этим не ловится — вне модели угроз (§2).

Сплошной поток не годится: случайный доступ невозможен, а AES-GCM на Android при расшифровке
буферизует весь шифротекст до конца — большой файл приводит к нехватке памяти.

### 7.3. Размер

Файловая система и сканирование отдают размер **открытого текста**. Он вычисляется из длины файла:
накладные расходы на заголовок и сегмент (nonce + тег) постоянны и записаны в заголовке.

## 8. Расширяемость

Метод шифрования и источник ключей — два независимых интерфейса.

```
StorageCipher
    id                    // "fserver.aes256gcm-seg.v1", пишется в заголовок
    nonceSize, tagSize
    seal(key, nonce, aad, plain) -> sealed
    open(key, nonce, aad, sealed) -> plain

StorageKeysStore
    current(sourceId) -> StorageKey(id, key)
    resolve(keyId) -> key | нет
    forget(sourceId)
```

- **Метод — только AEAD над сегментом.** Nonce, AAD (номер, флаг последнего), формат, заголовок, размер, миграцию и случайный доступ
  держит ядро — кастомному методу не нужно решать их заново.
- **Встроенные методы + методы приложения.** Приложение передаёт свои методы и источник ключей
  при конфигурации ядра. Метод выбирается по id из заголовка, поэтому после смены метода старые
  файлы читаются.
- **Неизвестный id метода — явная ошибка,** не тихая выдача сырых байт.
- **Ключи — схема конверта.** Ключ данных — один на источник; обёрнут ключом-обёрткой из
  системного хранилища ключей (Android Keystore) и хранится только обёрнутым. Ротация
  ключа-обёртки — переобёртка ключей данных, а не перешифровка файлов. Удаление ключа источника
  делает его файлы нечитаемыми (стирание через ключ).
- Ключ, который Keystore больше не разворачивает (данные приложения восстановлены на другом
  устройстве), не выдаётся: старые файлы — ошибка «нет ключа», новые пишутся под новым ключом.
- Если метод сегментного уровня не подходит (аппаратное шифрование, внешнее хранилище ключей),
  запасной путь — собственный декоратор файловой системы целиком.

### 8.1. Встроенный метод по умолчанию

AES-256-GCM посегментно. ChaCha20-Poly1305 в `javax.crypto` есть только с Android API 28, а
минимальная поддерживаемая версия ниже — он доступен лишь через стороннюю библиотеку.

## 9. Инварианты

1. Хэш содержимого — всегда от открытого текста.
2. Шифрование, перешифровка и ротация ключа не создают новую версию файла.
3. По сети не передаются ни шифротекст хранилища, ни id метода, ни ключи хранилища.
4. Общие хранилища (медиатека, Загрузки, share) не шифруются никогда.
5. Состояние шифрования файла определяет индекс; при политике `Required` открытый файл без
   отметки `pending` отвергается.
6. Замена файла при миграции атомарна.
7. Неизвестный метод — ошибка, а не открытый текст.

## 10. Открытые вопросы

- Если ядро на Rust, а метод приложения на Kotlin, каждый сегмент пересекает FFI. Нужен ли размер
  сегмента, настраиваемый методом.
