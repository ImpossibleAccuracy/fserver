# Техническое задание

### Кросс-платформенный файлообменник с открытой архитектурой

> Рабочий документ. Версия консолидирует исходное описание проекта и принятые проектные решения.
> Юридические пункты приведены как ориентиры, а не как заключение.

---

## 1. Общие сведения

### 1.1. Назначение

Кросс-платформенное приложение для передачи и хранения файлов между устройствами пользователя (в
перспективе — между разными пользователями) с открытой архитектурой. Работает по локальной сети и
через публичный сервер. Ключевой акцент — на удобстве пользователя и гибкости настройки как со
стороны клиента, так и со стороны сервера.

### 1.2. Основные принципы

- **Открытый исходный код.** Любой может собрать свой клиент или сервер.
- **Разделение «ядро ↔ UI».** Логика (транспорт, синхронизация, хранилище, шифрование) вынесена в
  независимое ядро; интерфейс общается с ним через документированный локальный API.
- **Документированный версионируемый протокол.** Сторонние клиенты и серверы совместимы за счёт
  открытой спецификации протокола и согласования версий при рукопожатии.
- **Сервер не доверяет клиенту.** Раз клиент может написать кто угодно, вся авторизация и проверка
  прав выполняются на стороне сервера. Ограничения в клиенте — только для удобства.
- **Удобство по умолчанию.** Онбординг, наглядные настройки, преднастройка сервером в один клик,
  шифрование «из коробки».

## 2. Термины и режимы работы

| Режим             | Суть                                                                                                                    | Направление                      | Назначение                       |
|-------------------|-------------------------------------------------------------------------------------------------------------------------|----------------------------------|----------------------------------|
| **Синхронизация** | Одинаковый набор файлов на всех устройствах                                                                             | Двунаправленное                  | Общий доступ к актуальным данным |
| **Хост**          | Файлы физически на одном устройстве/сервере, остальные обращаются по сети                                               | Клиент → хост                    | Модель «сетевой диск / NAS»      |
| **Разгрузка**     | Файлы переносятся на бэкап-устройство и удаляются с источника для освобождения памяти; локально остаётся доступ по сети | Одностороннее (источник → бэкап) | Освобождение памяти устройства   |

> Примечание к терминологии: режим, ранее названный «бэкапом», по факту является **разгрузкой памяти
** (тирингом): свежие файлы хранятся локально, старые переносятся на бэкап-устройство. Это не
> резервное копирование, поэтому в интерфейсе используется формулировка «разгрузка/архивирование», а
> не «бэкап». Полноценный бэкап с избыточностью может быть добавлен отдельным режимом позже.

## 3. Функциональные требования

### 3.1. Обнаружение и подключение

- Автообнаружение устройств в локальной сети (mDNS/Bonjour или аналог).
- Ручное подключение по адресу: IP или домен + порт.
- Сопряжение устройств (pairing) с обменом ключами и подтверждением нового устройства.
- Абстрактный слой транспорта с заделом под будущие типы соединения (USB, Bluetooth, Wi-Fi Direct).

### 3.2. Модель доступа и доверия

Тип доступа задаётся при настройке сервера:

- **Полностью открытый доступ** — подключиться может любой в сети. Режим высокого риска, требует
  явного предупреждения при выборе.
- **Доступ по QR** — доступ открыт, но сервер не публикует себя в локальной сети (не обнаруживается
  автоматически); подключение только по коду.
- **Доступ по паролю.**
- **Доступ по другим ключам** (расширяемый набор способов аутентификации).

Требования к коду доступа (QR/пароль/ключ):

- Код несёт не только адрес сервера, но и **отпечаток публичного ключа сервера** — для проверки, что
  клиент подключается именно к нужному серверу (доверие при первом подключении).

### 3.3. Транспорт и передача

- Проверка целостности переданных файлов по хэшу содержимого.
- Докачка при обрыве соединения (resumable).
- Потоковая передача крупных файлов.
- Опциональное сжатие «на лету».
- Транспорт всегда зашифрован (TLS/mTLS) независимо от режима.

### 3.4. Режимы работы (детально)

#### Синхронизация

- Двунаправленное поддержание идентичного набора файлов.
- **Порядок версий определяют векторы версий, а не время.** У каждого файла есть вектор «сколько
  правок сделало каждое устройство». Сравнение векторов даёт: версии равны, одна новее другой, или
  правки параллельные — только последнее является конфликтом. Время файла (mtime) и часы устройств
  для порядка не используются.
- **Новая версия — только при изменении содержимого** (другой хэш, другой размер, появление или
  удаление файла). Смена одной лишь даты модификации версией не является. Хэш может считаться
  лениво, но до его расчёта файл не перезаписывается и не удаляется входящей версией.
- **Удаление — это новая версия** (tombstone с увеличенным вектором), поэтому «удалили здесь,
  изменили там» определяется как обычный параллельный конфликт, а не молча побеждает удаление.
- Принятая с другого устройства версия (файл, удаление) записывается **с вектором отправителя**,
  без собственной правки. Одинаковое содержимое при разных векторах — не конфликт: векторы
  объединяются на обеих сторонах.
- **Автоматическое разрешение конфликтов: last-write-wins** — только для параллельных правок, и
  победитель выбирается детерминированно по метке гибридных логических часов (HLC) и id
  устройства, чтобы все устройства независимо пришли к одному результату.
- Устройство с часами, ушедшими вперёд больше допустимого порога, получает предупреждение.
- Режим разрешения — настройка пользователя (подробно — `HLC.md`, §6):
  - **Спрашивать** (по умолчанию) — файл пользователя без его решения не меняется: каждая сторона
    хранит свою версию, пока пользователь не выберет свою, чужую или обе;
  - **Last Write Wins** — автоматически, проигравшее содержимое не сохраняется.
- **В будущем:** локальная корзина восстановления для LWW; выбор стратегии через конфиг сервера,
  ручное разрешение и т.д.

#### Хост

- Все файлы на одном устройстве/сервере; остальные получают доступ по сети.
  - Доступ к файлам возможен только когда хост в сети.

#### Разгрузка

Схема работы:

1. Файлы создаются на устройстве-источнике и синхронизируются на бэкап-устройство.
2. Через заданный период (или по критерию вытеснения) приложение на источнике проверяет наличие
   файла на бэкап-устройстве.
3. При подтверждении копии файл удаляется с источника; локально остаётся доступ к нему по сети.

Требования:

- **Направление строго одностороннее** (источник → бэкап).
- Операция удаления с источника — это **вытеснение (`evict`), а не удаление (`delete`)**: движок
  синхронизации не должен трактовать освобождение памяти как удаление файла пользователем и
  распространять его на бэкап.
- Удаление локальной копии происходит **только после подтверждения копии на бэкапе по хэшу
  содержимого** (файл получен и надёжно записан).
- **Плейсхолдеры (stub-файлы):** после вытеснения пользователь продолжает видеть файл в интерфейсе
  как «облачный» — с локально сохранёнными метаданными и превью. По тапу файл докачивается по
  требованию.
- Критерий вытеснения: по возрасту (N дней) и/или по последнему доступу (LRU); возможность *
  *закрепить** файл, чтобы он никогда не вытеснялся.
- В UX явно проговорено: вытесненные файлы доступны только когда бэкап-устройство в сети.

### 3.5. Пользователи и аккаунты

- **Этап 1:** один пользователь — несколько устройств.
- **Этап 2:** сервер обслуживает нескольких пользователей.
    - У каждого пользователя свой аккаунт.
    - По умолчанию пользователь видит только свои файлы.
    - Пользователь может открыть свои файлы в **публичный read-only доступ**.
    - Изоляция данных между аккаунтами; квоты на объём.

### 3.6. Безопасность и шифрование

- **Шифрование по умолчанию:** файлы шифруются в хранилище (at-rest), транспорт шифруется всегда.
- **При включении ИИ:** сервер расшифровывает файлы для индексации. Соединение при этом остаётся
  зашифрованным.
- Модель, которую нужно честно отражать в интерфейсе: поскольку сервер способен расшифровать файлы
  для ИИ, ключи доступны серверу — это защита от кражи носителя, но не от недоверенного сервера.
- Переключатель ИИ сопровождается явным предупреждением о том, что сервер получит доступ к
  содержимому этих файлов.
- **Скоуп ИИ — по папкам:** расшифровке и индексации подлежат только папки, явно отданные
  пользователем под ИИ.
- Аутентификация и авторизация устройств/пользователей — на стороне сервера.

### 3.7. Просмотр и редактирование

- **Встроенный просмотр:** изображения, видео, аудио, PDF, текст (т.е. распространённые офисные форматы).
- **Лёгкое редактирование (MVP):** переименование, поворот/обрезка изображений.
- Полноценное видео/аудио-редактирование — вне рамок MVP.
- Для видео/аудио предпочтительна опора на системные кодеки платформы (лицензионные и
  производительные соображения).

### 3.8. UX, онбординг, преднастройка

- Онбординг для новых пользователей.
- Наглядные настройки и диагностика подключения.
- **Преднастройка со стороны сервера** — конфиг-профиль, применяемый в один клик (например, через
  QR-код или ссылку с ограниченным сроком жизни). Профиль включает адрес, способ доступа и отпечаток
  ключа сервера.

### 3.9. Экспорт данных

- Выгрузка всех файлов вместе с метаданными и настройками в единый архив (переносимость данных,
  миграция, соответствие праву на портируемость).

### 3.10. ИИ-помощник (будущее)

- Поиск и структуризация файлов на основе индексации содержимого.
- Работает только по папкам, явно включённым пользователем (см. 3.6).

## 4. Нефункциональные требования

### 4.1. Масштаб (MVP)

- Целевой ориентир — до **~1000 файлов** на хранилище.
- Ограничение задаётся **и по количеству файлов, и по суммарному объёму** (1000 заметок и 1000 видео
  по 4 ГБ — несопоставимые нагрузки).
- Лимиты ставятся **на каждое хранилище отдельно**; общего лимита на все хранилища устройства нет.
- На таком объёме допустимо полное сравнение наборов файлов при синхронизации и индекс в SQLite;
  дельта-синхронизация и сложный чанкинг не требуются.
- Интерфейсы движка спроектированы как заменяемые, чтобы позже добавить дельта-синк/масштабный
  индекс без переписывания.

### 4.2. Кросс-платформенность

- Перечень целевых платформ фиксируется отдельно (критично для оценки трудозатрат).
- Учитываются платформенные ограничения (фоновая активность, доступ к файловой системе, доступ к
  локальной сети — особенно на мобильных ОС).

### 4.3. Надёжность и производительность

- Восстановление состояния после сбоя без потери и повреждения данных.
- Локальное хранилище состояния (индекс, версии, метаданные) — например, SQLite.
- Плавная работа интерфейса при просмотре крупных медиафайлов.

### 4.4. Протокол и совместимость

- Версионируемый протокол с согласованием версий при рукопожатии; сервер корректно обслуживает
  клиенты более старых версий.
- Метаданные версии файла (вектор версий, HLC-метка, устройство-автор) — часть протокола: все
  клиенты и сервер ведут и передают их одинаково.
- Стабильная документированная граница «ядро ↔ UI» (локальный API), тоже версионируемая.

### 4.5. Лицензирование

- Выбор open-source лицензии фиксируется явно: copyleft (GPL/AGPL) ограничивает
  закрытые/коммерческие форки, permissive (MIT/Apache) — разрешает. Решение влияет на экосистему
  сторонних клиентов.

## 5. Архитектура (обзор)

```
┌─────────────────────────────────────────────┐
│                   Клиент(ы)                   │
│  ┌────────────┐        ┌───────────────────┐ │
│  │     UI     │ <────> │   Ядро (core)     │ │
│  │ (сменный)  │ лок. API│ транспорт, синк,  │ │
│  └────────────┘        │ хранилище, крипто │ │
│                        └─────────┬─────────┘ │
└──────────────────────────────────┼───────────┘
                                    │ версионируемый протокол
                    ┌───────────────┴───────────────┐
                    │            Сервер             │
                    │  авторизация · аккаунты ·     │
                    │  хранилище · (опц.) ИИ-индекс │
                    └───────────────────────────────┘
```

- **Ядро** — независимый компонент: обнаружение, транспорт (абстрагированный от типа соединения),
  движок синхронизации/разгрузки, шифрование, локальный индекс.
- **UI** — сменный слой поверх ядра.
- **Сервер** — источник истины по авторизации, аккаунтам, правам и (опционально) ИИ-индексу.

## 6. Этапность (роадмап)

1. **MVP.** LAN-обнаружение + прямая передача файлов между двумя устройствами + просмотр
   изображений/видео. Масштаб — до ~1000 файлов.
2. **Синхронизация** (векторы версий + LWW по HLC для конфликтов) + **хост-режим**. Шифрование по умолчанию.
3. **Публичный сервер:** модели доступа (открытый / QR / пароль / ключи), преднастройка в один клик,
   отпечаток ключа сервера.
4. **Разгрузка** (вытеснение с плейсхолдерами и докачкой по требованию) + экспорт в архив +
   расширенный просмотр форматов.
5. **Мультипользовательский сервер** (аккаунты, изоляция, публичный read-only) + **ИИ-помощник** (
   индексация по папкам).
6. **Новые транспорты** (USB, Bluetooth, Wi-Fi Direct), настраиваемые стратегии разрешения
   конфликтов.
