# Синхронизация: векторы версий и HLC

Как упорядочиваются изменения файлов и разрешаются конфликты.

## 1. Принципы

- **Порядок задаёт вектор версий, не время.** Время (HLC) нужно только чтобы выбрать победителя
  в настоящем конфликте. Сырой mtime для порядка не используется, только чтобы быстро найти
  кандидатов на изменение при сканировании.
- **Изменения обнаруживает ядро.** Файлы правят сторонние программы, поэтому «было ли изменение»
  решает сравнение диска с индексом, а не события приложения.
- **Удаление — новая версия** (tombstone). Строка индекса остаётся, иначе удалённый файл
  «воскреснет» при синхронизации со старым устройством.
- **Вытеснение (evict) — не версия.** Вектор не меняется, меняется только состояние строки.
  Вытесненный файл ничего не распространяет и не может выиграть конфликт.
- **Разрешение детерминировано.** Обе стороны независимо приходят к одному победителю и одной
  версии.

## 2. Версия файла

Версия = вектор версий + HLC-метка + устройство-автор. Часть протокола: передаётся в списке
файлов и в каждой операции, которая меняет файл на другой стороне (загрузка, скачивание,
удаление, принятие версии).

Идентичность файла выводится из канонического пути. Переименование = удаление + новый файл.

## 3. HLC

Метка — пара (физическое время в мс, логический счётчик), упакована в int64: 48 бит на мс,
16 на счётчик. Упакованное число сравнивается как метка.

- **Локальное событие:** если стена ушла вперёд — (стена, 0), иначе счётчик + 1. Метка никогда не
  идёт назад, даже если назад ушли часы.
- **Получение чужой метки:** стандартное правило HLC (максимум из своей, чужой и стены; счётчик
  от той, что дала максимум). Если чужая метка впереди стены больше чем на `MAX_DRIFT_MS`, её
  физическое время не принимается, выдаётся предупреждение.
- **Переполнение счётчика** переносится в миллисекунды.
- Последняя метка сохраняется, поэтому метки растут и между перезапусками.
- Чужие метки принимаются при получении списка файлов пира: берётся максимальная метка списка.
- Пакет локальных изменений одного сканирования получает последовательные метки.

## 4. Векторы версий

Вектор — счётчик правок файла по каждому устройству. Нулевые счётчики не хранятся, поэтому равные
истории — равные значения.

- **bump:** своё устройство +1 при каждой новой версии.
- **merge:** покомпонентный максимум.
- **compare:** равны / новее / старше / параллельны (у каждой стороны есть правка, которой не
  видела другая). Файл без версии считается пустым вектором — любая версионированная новее.

**Слияние версий:** вектор — merge обоих, HLC и автор — от более поздней по (HLC, автор).
Отдельный bump не нужен: обе стороны считают одно и то же.

## 5. Обнаружение локальных изменений

Источник сканируется целиком при каждом проходе синхронизации и сверяется с индексом по пути.

| На диске относительно индекса              | Результат                                     |
|--------------------------------------------|-----------------------------------------------|
| нет в индексе                              | новая версия, хэш не посчитан                 |
| был удалён/вытеснен, снова есть            | новая версия                                  |
| другой размер                              | новая версия                                  |
| тот же размер, другой mtime, хэш известен  | версия не меняется, хэш помечен устаревшим    |
| тот же размер, другой mtime, хэша нет      | новая версия                                  |
| нет на диске, в индексе присутствует       | новая версия-удаление                         |

Хэш считается лениво, когда он нужен для решения. Если новый хэш отличается от прежнего, это
правка, которой ещё нет в версии: выдаётся новая версия. Если файл изменился, пока считался хэш,
результат отбрасывается.

## 6. Планирование (зеркало)

По снимку «локальные / удалённые записи» для каждого файла:

- **Локальный файл вытеснен** — ничего.
- **Удалён на обеих** — только слияние версий, если истории разошлись.
- **Удалён на одной стороне:** решает вектор. Новее удаление — удалить на другой стороне; новее
  правка — передать файл. Равны или параллельны — конфликт. Перед удалением файла без хэша
  сначала считается хэш: в нём может быть неверсионированная правка.
- **Есть на обеих:**
  - одинаковый хэш — не конфликт, только слияние версий, если вектора разные;
  - хэш неизвестен при равном размере — сначала посчитать хэш, затем перепланировать;
  - разное содержимое: новее — загрузить, старше — скачать, параллельны или равны (правка,
    которую одна сторона не версионировала) — конфликт. Новее при вытесненных байтах — тоже
    конфликт.

За проход одно действие на файл. Раунды повторяются, пока остаются файлы без хэша (с лимитом).

## 7. Разрешение конфликта

Режим — настройка пользователя.

**Last Write Wins** (по умолчанию):

1. Победитель — версия с большей (HLC, автор). Равные версии — выигрывает устройство с большим id.
   Сторона без версии проигрывает.
2. Итоговая версия M — слияние обеих (§4).
3. Победитель переносится на проигравшую сторону под версией M: загрузка, скачивание или удаление.
4. Сторона-победитель сразу принимает M, так что обе сходятся в этом же проходе. Приём
   отклоняется, если файл изменился после планирования (хэш или состояние не совпали).

Проигравшее содержимое не сохраняется.

**Keep Both** — сохранить обе версии, проигравшую в `.conflicts/<path> (conflict <автор>
<hlc>).<ext>`. Имя детерминировано, поэтому одинаковые копии совпадут по хэшу.

## 8. Применение входящей версии

- **Файл:** если файл уже есть, байты пишутся во временный файл рядом; хэш сверяется с обещанным;
  затем атомарная замена переименованием. mtime выставляется от отправителя и записывается так,
  как его сообщит ФС, иначе следующее сканирование примет его за правку. Индекс получает версию
  отправителя.
- **Удаление по просьбе пира:** записывается под версией пира; без версии — как новая своя.
- **Принятие версии:** меняется только версия, и только если содержимое (или удаление) совпадает
  с ожидаемым.
