# Протокол соединения устройств

### Обнаружение, публичное приветствие, аутентификация, защищённая сессия

> Рабочий документ. Версия 1 (черновик). Описывает целевое устройство протокола независимо от
> текущей реализации. Порядок перехода от существующего кода описан в `Handshake Migration.md`.
>
> Опирается на ТЗ §3.2 (модель доступа и доверия), §3.3 (транспорт), §5 (версионирование протокола).

---

## 1. Задача

Разделить обмен между двумя устройствами на два уровня раскрытия:

- **Публичный уровень** — отвечает кому угодно, без участия пользователя. Несёт минимум, нужный
  чтобы понять *как* открывать защищённое соединение: диапазон версий протокола и перечень методов
  аутентификации.
- **Приватный уровень** — всё остальное (имя устройства, тип, словарь сообщений, возможности).
  Доступен только после успешной взаимной аутентификации, внутри зашифрованного канала.

До этого разделения любое входящее соединение требовало явного подтверждения пользователем, а
сведения об устройстве уходили в первом же нешифрованном кадре. Разделение снимает и то, и другое.

## 2. Модель угроз

### 2.1. От кого защищаемся

| Противник | Возможности | Что даёт разделение |
|---|---|---|
| Сканер портов / достижимый по WAN | Дозванивается на адрес, не видел объявлений в LAN | Не узнаёт имя, тип, идентификатор устройства |
| Устройство в скрытом режиме (доступ по QR, ТЗ §3.2) | — | Не публикует себя вовсе; публичное приветствие раскрывает минимум |
| Активный MITM в канале | Подменяет и вставляет кадры | Ломает аутентификацию (§6.2), сессия не поднимается |

### 2.2. От кого не защищаемся, осознанно

- **Пассивный наблюдатель в той же локальной сети.** Он видит объявления обнаружения, а те несут
  имя устройства по построению (§3). Сокрытие имени в публичном приветствии от него не спасает, и
  не должно преподноситься как защита.
- **Корреляция объявления с приветствием.** Объявление и приветствие связаны общим маршрутом
  (`host:port`), а не содержимым. Кто видел объявление — сопоставит.

### 2.3. Ключевая асимметрия, на которой стоит вся схема

Объявление — **добровольная трансляция**: устройство само решает, что и когда публиковать, и может
замолчать. Приветствие — **вынужденный ответ** любому, кто дозвонился, включая того, кто нашёл
устройство перебором портов.

Поэтому в объявлении допустимы данные, недопустимые в приветствии. Это не противоречие, а разная
природа канала.

## 3. Уровни раскрытия

| Данные | Объявление | Публичное приветствие | Запечатанный дескриптор |
|---|:--:|:--:|:--:|
| Диапазон версий протокола | ✓ | ✓ | — |
| Перечень методов аутентификации | ✓* | ✓ | — |
| Имя устройства | ✓ | ✗ | ✓ |
| Описание устройства | ✓ | ✗ | ✓ |
| Идентификатор устройства | ✓ | ✗ | ✓ |
| Тип устройства | ✗ | ✗ | ✓ |
| Словарь сообщений | ✗ | ✗ | ✓ |
| Максимальный размер кадра | ✗ | ✗ | ✓ |
| Отпечаток ключа | ✗ | ✗ | доказывается аутентификацией, не заявляется |
| Долговременный публичный ключ | ✗ | ✗ | обменивается внутри метода аутентификации |

\* Перечень методов объявляется только там, где приветствие приходит по проводу — как подсказка
для списка до соединения. Транспорт, фиксирующий метод сам (§8.2), в эфир его не кладёт: запрашивающая
сторона читает метод из объявления транспорта, что и достовернее, и дешевле.

Идентификатор устройства объявляется, хотя это и непрозрачная строка: рядом с ним в объявлении
стоит человекочитаемое имя, которое опознаёт устройство лучше любого идентификатора. Прятать
идентификатор, публикуя имя, — работа впустую. Граница проходит не по составу полей, а по
переключателю «вещать или молчать» (§3, правило 3).

**Отпечаток ключа в объявлении отсутствует принципиально.** Стабильный дайджест, транслируемый
непрерывно, — ровно то, по чему пассивный наблюдатель ведёт устройство из сети в сеть; имя такого
свойства не имеет, потому что его пользователь меняет, а ключ — нет.

Правила:

1. **Объявление не несёт ничего приватнее имени и описания.** Состав объявления — настройка, а не
   константа: публиковать ли имя, решает пользователь или профиль режима.
2. **Публичное приветствие не несёт ничего сверх минимума.** Добавление поля туда — изменение
   модели угроз, а не расширение возможностей.
3. **Устройство в скрытом режиме не объявляется вообще.** Это и есть весь механизм защиты имени от
   пассивного наблюдателя — переключатель режима, а не правило про поля.
4. **При расхождении объявления и запечатанного дескриптора побеждает дескриптор.** Объявление —
   заявление, дескриптор — то, что подтверждено соединением.

## 4. Поток

### 4.1. Обнаружение

Пользователь видит список устройств, собранный подсистемой обнаружения из объявлений. Список несёт
имя, описание и маршрут. Всё это **не подтверждено**.

### 4.2. Приветствие (probe)

Пользователь выбирает одно устройство. Клиент открывает соединение, обменивается публичным
приветствием и **закрывает соединение**.

Приветствие отвечает на два вопроса:

1. устройство ещё в сети;
2. какими методами к нему подключаться.

Подтверждения пользователем на принимающей стороне не требуется. Ответ на приветствие не создаёт
сессии, не порождает долгоживущего состояния и ничего не запоминает.

**Результат приветствия — справочный. Он не является входом безопасности и ему разрешено врать.**
Он нужен, чтобы показать пользователю правильную форму: поле пароля, ввод PIN или сверку ключей.

### 4.3. Соединение (connect)

Пользователь вводит требуемое, и клиент открывает **новое** соединение:

1. публичное приветствие — **повторно, в этом соединении**;
2. выбранный метод аутентификации, N раундов;
3. канал запечатывается;
4. взаимный обмен дескрипторами внутри канала;
5. готовность, сессия живёт.

Повторное приветствие — не перепроверка устаревших данных. Это **криптографический материал**:
байты приветствия из этого потока входят в транскрипт аутентификации (§6.2). Поэтому
`connect` **не принимает результат приветствия на вход и в нём не нуждается**.

```
┌── обнаружение ──────────────────────────────────────────────┐
│  объявления → список устройств (имя, описание — не проверены)│
└──────────────────────────────┬──────────────────────────────┘
                               │ пользователь выбрал одно
┌── приветствие (соединение №1) ▼─────────────────────────────┐
│  → HELLO      { версии, методы }                            │
│  ← HELLO_ACK  { версия, методы, параметры метода }           │
│  соединение закрывается                                      │
└──────────────────────────────┬──────────────────────────────┘
                               │ пользователь ввёл пароль / PIN / согласился сверить
┌── соединение (соединение №2) ▼──────────────────────────────┐
│  → HELLO      { версии, методы }          ┐                 │
│  ← HELLO_ACK  { версия, методы, параметры }┘ → в транскрипт  │
│  ⇄ AUTH × N   выбранный метод, полезная нагрузка непрозрачна │
│  ═══ канал запечатан ═══════════════════════════════════════ │
│  ⇄ DESCRIPTOR имя, тип, идентификатор, словарь               │
│  ⇄ READY                                                     │
└─────────────────────────────────────────────────────────────┘
```

### 4.4. Почему два соединения, а не одно

Рассматривались три варианта. Выбран третий.

| Вариант | Проблема |
|---|---|
| Одно соединение на всё | Соединение висит открытым, пока пользователь набирает пароль — минуты pre-auth ресурсов на каждого, кто дозвонился |
| Две фазы с передачей контекста между соединениями | Принимающая сторона обязана помнить, какое приветствие кому отправила. Ключевать нечем (другой исходящий порт, NAT), таблица ожидающих значений управляется атакующим, нужна политика истечения. Обходится stateless-куками, но это лишний механизм |
| **Приветствие отдельным соединением, `connect` повторяет приветствие у себя** | Состояния между соединениями нет вовсе. Привязка транскрипта достаётся бесплатно. Цена — один лишний обмен |

Третий вариант **устраняет класс атак «подменить фазу 1, пропустить фазу 2»**: передавать между
фазами нечего, значит и подменять нечего. Ложь в приветствии обнаруживается на `connect`, потому
что там приветствие звучит заново и привязано к аутентификации.

### 4.5. Расхождение приветствия и соединения

Приветствие сказало «пароль», соединение отвечает «только ключ» — прервать и запросить заново.
**Не продолжать по тому, что сказало приветствие.** Редкий путь, но именно на нём ломается тихое
понижение.

Если метод был закреплён после первого сопряжения (§6.4), применяется закреплённый — независимо от
того, что сказало любое из приветствий.

### 4.6. Порты прослушивания

Слушатель LAN-транспорта берёт **первый свободный порт из фиксированного списка**, по порядку:

| Порядок | Порт |
|:--:|---|
| 1 | 29470 |
| 2 | 29471 |
| 3 | 29472 |
| запасной | эфемерный (0) |

Список один для всех клиентов и сервера. Эфемерный порт — именно запасной вариант: он поднимает
слушателя, когда все три заняты, но записанный на него маршрут переживает перезапуск только
случайно.

Зачем фиксация:

1. **Записанный маршрут остаётся годным.** При эфемерном порте перезапуск двигает слушателя, и
   каждый сохранённый `host:port` протухает — устройство выглядит недостижимым, хотя оно в сети.
2. **Адрес без порта становится дозвонимым.** Введённый вручную адрес и QR без порта идут на первый
   порт списка.
3. **Входящий маршрут можно угадать.** У принятого сокета `socket.port` — исходящий порт пира, а не
   тот, который он слушает; дозвониться по нему нельзя никогда. Известен только хост, и список
   портов — единственное, что к нему добавляется.

Дозвон по этим правилам:

- маршрут с портом: сначала его собственный порт, затем остальные из списка;
- маршрут без годного порта (входящий, введённый адрес без порта): список целиком, по порядку;
- перебор продолжается **только если хост ответил отказом** (соединение отвергнуто — хост есть,
  слушателя на этом порту нет). Таймаут или недостижимый хост означают, что устройства нет в сети,
  и перебор остатка списка лишь умножает ожидание.

Модели угроз это не меняет: §2.3 уже считает дозвон перебором портов возможностью противника, а
приветствие обязано отвечать любому, кто дозвонился. Фиксированный порт делает такой перебор дешевле,
но не даёт ничего сверх того, что даёт публичное приветствие.

## 5. Форматы

### 5.1. Публичное приветствие

```
PublicHello {
    minVersion: i32          // минимальная поддерживаемая версия протокола
    maxVersion: i32          // максимальная; в ответе обе равны выбранной
    methods:    [AuthMethodId]
    params:     bytes?       // параметры выбранного метода, только в ответе
}
```

Три обязательных поля. Всё, что можно вынести — вынесено:

- **Максимальный размер кадра исключён.** До аутентификации бесполезен, а согласование его с
  непроверенным собеседником — это позволить ему двигать лимит выделения памяти. До запечатывания
  канала каждая сторона применяет **свой локальный** лимит; согласование переезжает в дескриптор.
- **Перечень шифров исключён.** Схлопывается в идентификатор метода.
- **Разовое значение (nonce) не нужно.** Оно требовалось только для связывания разных соединений;
  при схеме §4.3 связывать нечего.

### 5.2. Идентификатор метода аутентификации

Строка, кодирующая паттерн рукопожатия и примитивы целиком, например
`spake2-x25519-chacha20poly1305`. Отдельного согласования шифров нет — метод определяет всё.

Набор расширяем (ТЗ §3.2: «доступ по другим ключам — расширяемый набор способов аутентификации»),
поэтому это идентификатор, а не перечисление с фиксированным составом. **Второго словаря режимов
доступа не заводится** — иначе два имени одного понятия разъедутся.

### 5.3. Дескриптор устройства

Отправляется только внутри запечатанного канала.

```
PeerDescriptor {
    deviceId:      string
    displayName:   string
    description:   string?
    kind:          enum?      // Desktop | Laptop | Phone | Tablet | Nas
    dictionary:    DictionaryDescriptor
    maxFrameSize:  i32
}
```

`maxFrameSize` — единственное поле дескриптора, которое становится ограничением на **наши**
отправки, поэтому у него есть нижняя граница: заявленный размер меньше минимального отвергается
как протокольная ошибка. Иначе собеседник объявляет крошечный кадр, и канал, формально поднятый,
не пропускает ни одного сообщения. Минимум задаётся тем, что рукопожатие дробить нельзя: дескриптор
и раунды аутентификации — цельные кадры.

Долговременный публичный ключ **не отправляется**. Он доказывается самой аутентификацией.
Заявлять в дескрипторе то, что уже доказано криптографией, — источник расхождения между
«заявлено» и «доказано».

Объявленные и подтверждённые сведения — **разные типы**, а не один тип с необязательными полями.
Смешение приводит к невозможности ответить, проверено ли конкретное поле.

### 5.4. Виды кадров

```
HELLO       публично, открытым текстом
HELLO_ACK   публично, открытым текстом
AUTH        N раундов выбранного метода; полезная нагрузка непрозрачна для транспортного слоя
─────────── ниже — только внутри запечатанного канала ──────────
DESCRIPTOR
READY
MESSAGE / REQUEST / RESPONSE / ERROR
CHUNK
PING / PONG / CLOSE
```

Обмен дескрипторами — **один вид кадра, не пара запрос/ответ**. После запечатывания канал дуплексный,
и ждать чужой дескриптор перед отправкой своего незачем.

### 5.5. Дробление сообщений

Сообщение прикладного уровня не обязано помещаться в кадр: файл, снимок индекса или ответ со
списком файлов крупнее согласованного `maxFrameSize`. Дробит и собирает **сессия**, а не словарь —
прикладной код отдаёт сообщение целиком и о кадрах не знает. Иначе про лимит кадра пришлось бы
знать каждому отправителю, а он у каждого транспорта свой.

Кусок едет в кадре `CHUNK`, полезная нагрузка которого:

```
Fragment {
    kind:   u8     // MESSAGE | REQUEST | RESPONSE — чем станет собранное
    index:  i32    // с нуля
    total:  i32
    part:   bytes  // остаток кадра; собственной длины не несёт
}
```

Идентификатор сообщения и идентификатор корреляции берутся у дробимого сообщения и **одинаковы у
всех его кусков**. Поэтому куски двух сообщений могут чередоваться в канале, а собранный `REQUEST`
по-прежнему сходится со своим `RESPONSE`. Кадры управления (`PING`/`PONG`/`CLOSE`) идут своей
очередью и не ждут конца передачи.

В один кадр помещается `maxFrameSize` за вычетом заголовка кадра, довеска запечатывания и — для
дробного сообщения — заголовка `Fragment`. Кадр сверх лимита не пишется в канал **никогда**:
принимающая сторона обязана его отвергнуть, и стоит это всей сессии, а не одного сообщения.

Правила принимающей стороны:

- `kind` — только `MESSAGE`, `REQUEST` или `RESPONSE`. Кадры управления и рукопожатия не дробятся.
- `index` в пределах `0..total-1`, `total >= 1`; повторный индекс игнорируется.
- Куски под одним идентификатором обязаны совпадать по `kind` и `total`; расхождение — вся сборка
  выбрасывается.
- Объём собираемого сообщения ограничен, и число одновременных сборок тоже. При переполнении
  выбрасывается **самая старая** сборка: сообщение, остаток которого не придёт уже никогда
  (отправитель умер, связь пересобралась), иначе занимало бы место до конца сессии.
- Незавершённые сборки выбрасываются при потере связи и при её пересборке.

`CHUNK` — часть протокола, а не согласуемое расширение: реализация обязана уметь собирать. Старые
сборки отрезаются повышением минимальной версии (§8.5).

## 6. Аутентификация

### 6.1. Метод как заменяемый интерфейс

```
AuthMethod {
    id:  AuthMethodId                      // то, что объявляется в приветствии
    run(io, role, prologue) -> AuthOutcome // ключ сессии + доказанный ключ собеседника
}
```

Транспортный слой владеет прокачкой кадров (`AUTH`), метод владеет криптографией. Полезная нагрузка
`AUTH` для транспортного слоя непрозрачна.

Целевой набор ложится на паттерны Noise Protocol Framework:

| Способ доступа (ТЗ §3.2) | Метод |
|---|---|
| Сверка отпечатков | обмен ключами + короткая строка аутентификации, сверяемая пользователем |
| Пароль / PIN | сбалансированный PAKE (SPAKE2 либо CPace, см. §8.1) |
| QR / ключ | статический ключ, паттерн `IK`; QR несёт отпечаток (ТЗ §3.2) |

### 6.2. Привязка транскрипта

Байты `HELLO` и `HELLO_ACK` **этого соединения** подаются в аутентификацию как prologue (штатный
параметр Noise ровно для преднегоциации).

Следствие: подмена приветствия меняет выводимые ключи и рушит аутентификацию. Обнаружение
происходит автоматически, отдельной проверки в коде не существует и написать её забыть нельзя.

### 6.3. Методы, предоставляемые транспортом

Некоторые транспорты дают аутентифицированный канал сами. Nearby Connections выводит цифры
подтверждения из обмена ключами канала; сверка их пользователем — это полноценная короткая строка
аутентификации поверх обмена ключами, а не заглушка.

Транспорт объявляет это статически, **до открытия соединения**:

```
ChannelSecurity =
    | None                          // сырые байты, требуется полный обмен ключами
    | Sas(method: AuthMethodId)     // канал зашифрован и аутентифицируется сверкой строки
```

Объявление статично, а **строка сверки — свойство соединения**, поэтому здесь только
идентификатор метода; сама строка приходит вместе с конкретным соединением.

Доступные методы = объявленные настройкой ∪ объявленный транспортом.

**Три правила, без которых схема ломается:**

1. **Транспортный метод выбирается собственной политикой, никогда не по предложению собеседника.**
   Проверка локальная и на обеих сторонах: идентификатор принимается только если *собственный*
   транспорт этого соединения объявил `Sas` с этим идентификатором. Иначе враждебное устройство по
   обычному TCP заявит транспортный метод и пройдёт без аутентификации вовсе.
2. **Строка аутентификации подтверждает канал, а не личность.** После сверки известно только «я
   говорю с устройством, на экране которого эти цифры». Долговременного ключа нет — его нужно
   получить и закрепить внутри уже аутентифицированного канала.
3. **Вердикт сверки не кешируется никогда.** Кешируется только закреплённый ключ. Кеш «транспорт
   сказал да», применённый к другому соединению, — прямая дыра.

Правило 1 — частный случай общего инварианта §7.2.

### 6.4. Закрепление и доверие при первом подключении

После успешной аутентификации доказанный публичный ключ собеседника закрепляется вместе с
показанным именем.

- Смена имени при том же ключе — норма, пользователь переименовал устройство.
- **То же имя при другом ключе — атака**, и её необходимо показать пользователю, а не разрешить
  молча.
- Метод аутентификации закрепляется вместе с ключом. Попытка соединения слабейшим методом, чем
  закреплённый, — понижение, а не выбор.

Это единственное, что делает объявленное имя со временем осмысленным: само по себе оно не
проверено никогда, а для парольного метода не проверяемо в принципе — провал PAKE неотличим от
«неверный пароль».

## 7. Инварианты

Нарушение любого из них — дефект безопасности, а не стилистическое замечание.

1. **Публичный уровень не несёт приватных сведений.** Добавление поля в приветствие требует
   пересмотра §2, а не только §5.1.
2. **Транспортный слой доверяет своим SPI и не доверяет собеседнику никогда.** SPI — код,
   собранный в этот процесс. Собеседник — байты из сети. Выглядят одинаково, класс разный. Что
   именно SPI передаёт, ядро проверить не может и не пытается; это ответственность реализации SPI.
3. **Ничто, полученное до аутентификации, не влияет на решения безопасности.** Результат
   приветствия — только для отображения.
4. **Согласуемые параметры входят в транскрипт аутентификации.** Иначе они управляются противником.
5. **Понижение метода аутентификации относительно закреплённого невозможно молча.**
6. **До запечатывания канала лимиты кадров локальные, не согласованные.**
7. **Отказ ограничивается по частоте.** Перечень методов в приветствии — наводка («тут PIN»);
   счётчик неудачных попыток на принимающей стороне, стойкий между соединениями, с задержкой —
   обязателен, а не желателен.
8. **Проверки на стороне клиента — только удобство интерфейса** (ТЗ §1.2). Решает принимающая
   сторона.
9. **Сборка дробного сообщения ограничена принимающей стороной.** Сколько кусков придёт и какого
   размера, объявляет собеседник; без потолка на объём сборки и на число одновременных сборок это
   управляемое им исчерпание памяти.

## 8. Открытые вопросы и известные ограничения

### 8.1. Выбор PAKE

Требование: парольный метод обязан противостоять офлайн-перебору по перехваченному транскрипту.
Схема «пароль → функция вывода ключа → предварительно разделённый ключ в Noise» этому **не**
удовлетворяет: ключ низкой энтропии вскрывается словарём офлайн. Именно от этого защищает PAKE.

Развилка, которую нужно закрыть до того, как интерфейс пообещает ввод PIN:

- есть проверенная реализация PAKE на целевых платформах → пароль может быть коротким
  пользовательским (PIN);
- нет → парольный режим обязан работать на **сгенерированном коде высокой энтропии**, то есть по
  сути тем же кодом доступа, что и QR, только в текстовой форме.

Мина совместимости: SPAKE2 существует в несовместимых вариантах (RFC 9382 против более ранних
черновиков — разные точки, разное хеширование транскрипта, разный порядок строк идентичности). Две
библиотеки, обе называющие себя SPAKE2, могут не договориться. **Вариант и набор примитивов
фиксируются письменно здесь, до выбора библиотеки**, и проверяются тестовыми векторами между
реализациями для разных платформ.

Альтернатива к рассмотрению — CPace, выбранный CFRG в качестве рекомендуемого сбалансированного
PAKE. Выбор делается осознанно, а не по доступности биндинга под конкретную платформу.

### 8.2. Транспорты без анонимной фазы

Nearby Connections не позволяет обменяться байтами до системного подтверждения соединения. Данные
о конечной точке при этом передаются **до** акцепта — их и следует использовать как источник
приветствия.

Формализуется третьим значением в возможностях транспорта: источник приветствия — `провод`,
`транспорт` или `отсутствует`. При источнике `транспорт` приветствие не открывает соединения вовсе
и возвращается из данных обнаружения. Это же закрывает случай прямого адреса по QR, где объявления
нет.

**Перечень методов при этом в эфир не идёт.** Транспорт, объявивший `ChannelSecurity.Sas`,
фиксирует метод сам, поэтому запрашивающая сторона читает его из **собственного объявления
транспорта**, а не из широковещания пира. Достовернее (локальный код против заявления из сети) и
дешевле — данные о конечной точке жёстко ограничены по размеру, и тратить их на уже известное
незачем. Из эфира при этом источнике берутся только версии протокола.

Ограничения источника `транспорт`:

- размер данных о конечной точке жёстко ограничен — замерить фактический предел до того, как туда
  закладывается что-либо новое;
- это **широковещание**: одинаковое содержимое всем, отвечать разным по-разному невозможно. Значит
  приветствие через транспорт всегда уровня объявления и приватнее объявления быть не может.

### 8.3. Nearby как транспорт разовой передачи

Если из сессии Nearby не сохраняется ничего, то цифры сверяются каждый раз, а устройство,
сопряжённое по Nearby, при встрече по другому транспорту неузнаваемо — долговременного ключа нет.

Это допустимое продуктовое решение, но оно должно быть **решением**, иначе всплывёт как дефект
«почему после сопряжения устройство не в доверенных».

Развилка: сохранять из сессии Nearby *только доказанный публичный ключ* (сессию — нет), либо не
сохранять ничего. Первое даёт узнаваемость между транспортами почти даром.

### 8.4. Стоимость для интерфейса

До аутентификации известно только то, что объявлено. Список устройств показывает непроверенные имена
и обязан это отражать — либо визуально, либо через состояние «подтверждено» после первого
успешного сопряжения. Это прямое следствие цели, а не побочный дефект.

### 8.5. Совместимость версий

Изменение состава приветствия ломает саму точку согласования версий, потому что согласование живёт
в нём. Совместимость со старым составом не изображается: поднимается минимальная поддерживаемая
версия протокола, старая отрезается. Допустимо, пока проект на ранней стадии; после первого
публичного выпуска — уже нет.
